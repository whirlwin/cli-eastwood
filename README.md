<h1 align="center">There are two kinds of people... those with agent CLIs, and those who grep</h1>

`clewd` is a small CLI that does almost nothing until you teach it. New
commands live as TypeScript files in `~/.config/cli-eastwood/`, and clewd
loads them every time it starts, so there's nothing to rebuild, publish or
reinstall. It ships as one self-contained binary that upgrades itself.

## Install

```sh
curl -fsSL https://raw.githubusercontent.com/whirlwin/cli-eastwood/main/install.sh | sh
```

This installs to `~/.local/bin/clewd`, verifying the SHA-256 checksum. Set
`CLEWD_INSTALL_DIR` to put it elsewhere, or `CLEWD_VERSION` to pin a release.
Prebuilt for macOS and Linux on arm64 and x64.

## Teach it a trick

```sh
clewd ext new hello     # writes ~/.config/cli-eastwood/extensions/hello.ts
clewd hello --name Clint
```

An extension is a file that default-exports an object:

```ts
import type { Extension } from "../clewd";

export default {
  name: "hello",
  commands: [
    {
      name: "hello",
      description: "Say hello",
      flags: { name: { type: "string", short: "n", default: "world" } },
      async run(ctx) {
        const branch = (await ctx.$`git branch --show-current`.nothrow().text()).trim();
        console.log(`Hello, ${ctx.flags.name}! You're on ${branch || "no branch"}`);
      },
    },
  ],
} satisfies Extension;
```

`import type` is erased when clewd loads the file, so the binary doesn't need
to resolve anything. `clewd ext init` (run automatically when needed) writes
`clewd.d.ts` and a `tsconfig.json` next to your config, which gives your
editor full types and autocomplete for `ctx`.

### What a command gets

| `ctx.` | |
| --- | --- |
| `args`, `flags` | Positional arguments and parsed flags (`--x v`, `--x=v`, `-x`, `--no-x`, `--`) |
| `$` | Bun's shell: `` await ctx.$`kubectl get pods`.text() `` |
| `store` | Persistent key/value store per extension, under `~/.local/state/cli-eastwood/` |
| `config` | Your `config.ts`, including any custom keys you add |
| `log` | `info`, `warn`, `error`, `debug` to stderr (`CLEWD_DEBUG=1` shows debug) |
| `run(argv)` | Run another clewd command, so extensions can build on each other |
| `paths`, `version` | Where clewd keeps things, and which clewd this is |

Commands can nest with `subcommands`, have `aliases`, and return a number to
set the exit code. Help (`--help`) is generated for every command.

Set `CLEWD_NO_EXTENSIONS=1` to skip `config.ts` and every extension, which is useful when an extension is misbehaving.

### Hooks

Extensions can also watch every command, built-in or not:

```ts
import type { Extension } from "../clewd";

export default {
  name: "timing",
  hooks: {
    beforeCommand(ctx) { ctx.store.set("start", Date.now()); },
    afterCommand(ctx, cmd) { ctx.log.debug(`${cmd.name} took ${Date.now() - ctx.store.get<number>("start")!}ms`); },
    onError(ctx, cmd, err) { ctx.log.error(`${cmd.name} failed`); },
  },
} satisfies Extension;
```

### Imports

Extensions can import `node:*` modules, Bun APIs and relative files. npm
packages work too, as long as a `node_modules` folder sits next to the file
that imports them (run `bun add <pkg>` inside `~/.config/cli-eastwood/`).

## Configuration

Everything lives in `~/.config/cli-eastwood/` (or `$XDG_CONFIG_HOME/cli-eastwood/`):

```
~/.config/cli-eastwood/
├── config.ts          optional, see below
├── clewd.d.ts         types, generated by clewd
├── tsconfig.json      for your editor, generated once
└── extensions/
    ├── hello.ts       every *.ts here is loaded, in name order
    └── timing.ts
```

```ts
// config.ts
import type { Config } from "./clewd";

export default {
  disabled: ["timing"],                  // skip these extensions
  upgrade: { checkOnStartup: true },     // daily "new version" notice
  extensions: [/* inline extensions, loaded first */],
  team: "platform",                      // anything else: read it via ctx.config
} satisfies Config;
```

A broken extension never takes clewd down. It's skipped with a one-line
warning, and `clewd ext doctor` tells you what went wrong. Built-in commands
always win a name clash; between extensions, the first one loaded wins and
`ext doctor` reports the clash.

| Command | |
| --- | --- |
| `clewd ext new <name>` | Scaffold an extension |
| `clewd ext list` | Loaded extensions and their commands |
| `clewd ext doctor` | Load errors and name collisions (exit 1 if any) |
| `clewd ext init` | Write or refresh `clewd.d.ts` and `tsconfig.json` |

## Upgrading

```sh
clewd upgrade            # latest release
clewd upgrade --check    # just tell me
clewd upgrade --version 0.1.0
```

clewd downloads the release for your platform, checks it against
`checksums.txt`, makes sure it runs, then swaps itself in atomically. If
anything fails, the binary you have is left alone. Once a day it also checks
for a new version in the background (with a 1 second timeout) and mentions it
after your command finishes. Set `upgrade.checkOnStartup: false` to turn that
off. `GITHUB_TOKEN` is used for the API call when set.

Every release binary carries a build provenance attestation, so you can
check that it was built by this repo's release workflow:

```sh
gh attestation verify "$(command -v clewd)" --repo whirlwin/cli-eastwood
```

## Why TypeScript on Bun

Runtime extensibility needs a language that can load new code without a
compile step, while the CLI itself should still be a single binary. Bun does
both: `bun build --compile` produces a standalone executable that can still
`import()` and transpile `.ts` files from disk. Extension authors get static
types without installing anything. Go plugins break across compiler versions,
and embedding Lua or Starlark would make everyone learn a second language for
a thinner API.

## Development

```sh
bun install
bun test
bun run typecheck
bun run build            # dist/clewd
bun src/main.ts --help   # run from source
```

Releases are cut by pushing a `v*` tag. The release workflow builds all four
binaries (the macOS ones on macOS, ad-hoc signed), writes `checksums.txt` and
publishes a GitHub release.
